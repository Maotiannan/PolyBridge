# 屏幕字幕连续显示与异常复核 · 0.5.6

## 需求与现场证据

机主原话：「我发现使用屏幕字幕功能的时候，达到屏幕你的框的字数上限后就不会动了，虽然后面回到软件里还是完整记录的，但是这一开始的体验不好，不能做成达到框框上限字数后自动滚动向下显示吗？或者取消上限？」以及「而且有时候会出现bug，明明是一段正常的语音，变成了图里的这个样子，啥情况，怎么解决？」

补充：「whatsapp business，原语音是法语。我没注意，反正播放的时候就已经出现了这样」。机主明确授权读取手机历史。

2026-11-04 的只读检查确认：对应字幕会话保存了一个被错误标为中文的条目，原文 752 字符，其中同一个英文短语出现 48 次；不是仅在浮窗绘制时重复。采集为 16 kHz 单声道，约 70 秒，系统没有静音采集。只记录结构与计数，不把个人会话、语音或凭据写入仓库。原始音频及当时的云端逐条响应未保存，不能声称恢复了旧录音。

## 方案

- 将小窗原文和译文各放入高度受限、文字不截断的滚动区域。全文仍保留整次会话。新内容默认跟随到末尾；用户向上浏览时暂停跟随，显示「回到最新」。折叠、展开和同一句持续增长均使用明确的跟随状态。
- 全文每段显示自己的翻译方向，避免最后一段的标题被误认为整个历史的方向。标题、拖动和停止保持原有位置与作用。
- 把异常检测封装为纯文本质量检查。只识别长串机械循环，不删掉正常的重复强调或重复朗读。异常的实时预览显示核对状态，不作为正常字幕刷屏。
- 屏幕字幕会话在手机内存保留有上限的近期 PCM。仅异常条目触发一次独立语音识别和翻译，重新读取服务返回的语种，不沿用已出错的方向。音频不落盘，正常条目不增加复核请求。
- 每个异常条目最多复核一次，并发、缓存和结束等待有上限。停止后不得由迟到结果重开字幕或污染下一次会话。超时、缺少完整片段或二次结果仍异常时，保存明确的未确认状态并继续后文，不把截短的错误内容伪装成正确译文。
- 旧历史保持原始数据，不凭猜测改写原文。新产生的异常条目持久化未确认状态。现有雨声过滤、抢话和正常长语音保存不改变。

协议依据：[千问实时事件](https://help.aliyun.com/zh/model-studio/live-translator-server-events)区分临时完整快照与增量；[独立语音识别](https://help.aliyun.com/zh/model-studio/qwen-asr-api-reference)在未指定源语言时返回识别语种。继续使用现有 3.5 实时模型，不顺带迁移模型。

## 实施与验收

1. 先给长循环、正常重复、连续文本快照和重复事件建立失败用例，再实现可复用的质量检查。
2. 给有界音频回看、重连、方向纠正、复核失败、停止后迟到结果建立接口回归；独立 ASR 的 HTTP 测试核对未强制旧语种以及按返回语种翻译。
3. 抽出字幕内容视图，把窗口定位与文字呈现分开。用 Android 视图接口检查长句增长后末尾可见、手动上翻不被拉回、点「回到最新」恢复、全文和各段语言标记。
4. 构建 0.5.6，手机上用隔离字幕记录验证滚动；用固定法语和受控异常事件验证真实千问复核；再验证实际应用播放共享。所有手机测试串行，不在测试期间运行安装脚本。
5. 同步 README、验收矩阵、版本、证据与本地 Git。核对已安装包摘要，结束采集并恢复临时设备设置。

本轮在 `codex/caption-scroll-recovery` 分支内执行，不使用子代理。密钥始终留在手机，现场原文不作为仓库测试素材。

## 实际边界

- 检查的是长机械循环，不能识别所有普通错译；短重复强调照常显示，持续循环仍需核对原音。
- 缓存最近 90 秒、复核单段最多 60 秒、最多两个待处理条目。缺少结束边界、超出长度或音频已过期时，显示未确认并继续后文。
- 字幕没有字符截断上限，但浮窗高度受屏幕大小约束；停止后全文仍受原有本地会话保留策略管理。
- 本次后续上机复验时，那条旧异常已不在当前历史。只读检查未改写历史；当时诊断文件修改时间早于本轮安装。旧条目的重新运行检查记为缺少样本，不冒充通过，也不重建私人记录。真实 WhatsApp 原语音未重放，无法保证它在当前版本一定正确。
