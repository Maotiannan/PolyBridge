# 翻译为什么会漏、会碎：处理链路与调节说明

状态：2026-11-04，对 0.6.0 源码的排查与待确认改进建议。不是修复发布说明。

本轮电脑未检测到 USB 设备，未读取事故现场的手机配置、历史或事件记录；未发起新云端请求。以下明确区分源码事实、待验证原因和拟开放选项。

用户已确认：碎片化发生于**屏幕字幕听 WhatsApp 语音**，不是麦克风自由监听。优先验证应用播放采集、人声过滤、模型句子完成/取消和字幕合并；不能把调整耳机麦克风作为此次修复。

## 用户参与的边界（最新澄清）

用户希望共同设计算法策略和实际体验，不希望承担账号、连接、配置格式、编译部署等工程工作。下文的“可调项”是设计讨论的工具箱，不代表要把全部内部数值做成设置滑块，也不要求用户自行调好软件。

用户参与：怎样断句、怎样判断同一条语音、能接受多少延迟和字幕修订、是否优先保住轻声、什么情况下应重听原音。开发负责：提出有证据的候选方案、接入与许可核验、模块封装、参数映射、自动化测试、持久化、错误恢复与合理默认值。

## 开源算法候选与比较方法（研究建议，尚未选型或接入）

当前 Silero 用于判断有没有人声，配合放行/静音；它不是从“人声和雨声同时存在”的音频里分离噪声的降噪器。引入语音增强算法是在补不同的能力，不能只修改现有人声阈值来替代。

| 候选 | 上游可核实事实 | 本项目的研究定位 |
|---|---|---|
| GTCRN | 官方提供轻量模型和流式实现；有 ONNX 部署路径 | 优先评测的神经降噪候选。项目已使用 ONNX Runtime，但仍需验证模型转换、状态管理、手机耗时和识别保真，不能直接视为可用 |
| RNNoise | 官方为 C 降噪库，示例处理 48 kHz 音频 | 作为另一条独立降噪对照；与本项目 16 kHz 云端输入之间的转换开销、音质和新版本权重均计入比较 |
| WebRTC APM | 官方将其作为麦克风处理模块，包含回声消除、降噪、自动音量等，可独立使用 | 优先评估麦克风监听与同时播报场景；也可将其降噪单独作为对照，不把整套通话处理强加给应用播放采集 |

来源：[GTCRN 官方](https://github.com/Xiaobin-Rong/gtcrn)、[RNNoise 官方镜像](https://github.com/xiph/rnnoise)、[WebRTC APM 官方](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_processing/g3doc/audio_processing_module.md)。GTCRN 仓库的对比表使用 RNNoise 2018，不能据此宣称胜过 RNNoise 当前版本，更不能据此判断本项目法语听写准确率。

两类输入分开研究：

- **屏幕字幕：**应用原始音频作为对照，分别测试不额外降噪、GTCRN、RNNoise、APM 降噪。不开本机扬声器回声消除，因为该输入不是本机麦克风收录的扬声器回声；原录音自身带来的噪声仍可能需要降噪。不同候选不默认串联。
- **麦克风监听：**先核对手机/耳机已做的处理，再比较系统回声消除与 APM 回声处理；软件消回声需要正确的播报参考与时序。后面至多选一种额外降噪策略作为起点，防止同类处理重复。人声判断与整段边界保持独立。

评估必须包括原始音频，不以“听起来更安静”或论文分数作为唯一标准。使用同一份清晰中文/法语、轻声、辅音与句首、雨声/风扇、突发噪声、混合背景说话和语音压缩样本，分别检查：

1. 原文漏字、错字、数字/否定/人名是否保留；清晰输入不能明显退化。
2. 噪声独立出现时是否生成假字幕，正常短回复是否误删。
3. 一条长语音完整性、字幕提前量、最终完成时间和修订频率。
4. Fold5 连续运行耗时、积压、内存、发热与耗电；电脑实时不等于手机稳定。
5. 相同千问调用方案下的实际用量。先做本地处理筛选，再在既有费用约束内做云端对比；不扩预算，不把预留当实付。

同样的比较方法适用于其他环节：停顿断句与结合文字完整性的断句；一体翻译与独立听写后翻译；立即显示可修订草稿与等待稳定句子；短上下文与同一条语音内的上下文。每次只改一个因素，输出可重放的自动化结果，让用户决定体验取舍，不让用户猜内部数值。

当前待讨论的首个体验选择：屏幕字幕是先出明显标注的暂定译文、后面补全修订，还是更愿意等意思完整后再显示较稳定的句子。无论选择哪种，都不应静默改写已确认历史、丢失前句，或把内部处理分段变成几十条独立语音。

## 先看结论

换模型不能单独解决整段语音被拆成很多条的问题。应用需要把以下四种边界分开：

1. **声音小包**：为了及时上传，声音被切成约 0.1 秒的小包。这不应产生一条历史。
2. **模型的一句话**：云端根据停顿或其他规则判断一句结束，返回原文和译文。
3. **用户的一条语音**：例如 WhatsApp 一条两分钟语音，内部可以有很多句话和长停顿。
4. **屏幕与历史的一条记录**：应按用户理解组织，不能简单照搬模型的每次分句。

目标应是：**边播放边翻译，句子陆续补到同一条语音里；整段结束后收尾，而不是等整段结束才开始翻译。**

## 已查到的实现事实

| 位置 | 0.6.0 当前行为 | 对体验的影响与证据边界 |
|---|---|---|
| 本机人声过滤 | 麦克风监听、应用播放字幕都经过同一套过滤；未通过的声音替换成等长静音 | 能减少雨声误识别，也可能误删轻声或辅音。未取得用户原音，不能认定此次一定发生了误删 |
| 云端停顿断句 | LiveTranslate 3.5：只出文字时 1.8 秒、生成译音时 1.2 秒；Audio 3.1、Omni 3.8：固定 0.8 秒 | 切换模型同时改变断句。另一个耦合是：自由监听关闭自动朗读后，也会使用 1.8 秒，而不是继续使用 1.2 秒 |
| 历史组织 | 每个完成的模型句子直接保存为独立条目 | 尚无“同一条播放语音”的合并层；模型分得越多，记录就越碎 |
| 播放源边界 | 采集只按指定应用筛声音，没有接入播放状态来判定整条语音结束 | 用户要求的“来源停止 2 秒再开始新段”尚未实现；不能把现有静音判断冒充该功能 |
| Audio 3.1 行为 | 使用语音对话接口，用文字要求只做翻译；采用自动停顿断句；历史上下文限制为 1 轮 | 不是专用同传的直接替代。官方描述在新语音到来时可能取消当前回复，需用实际事件验证漏译是否由此产生 |
| 返回结果关联 | 翻译回复按“最早尚未匹配回复的输入句子”关联；回复创建时若还没有输入句子就被忽略 | 存在事件先后顺序与关联的排查点；没有此次事件记录，不能宣布它就是事故根因 |
| 异常复核 | 临时缓存位于本机过滤之后，仅对被判为异常的完整片段重新识别、翻译一次 | 不是过滤前的完整原音，不能恢复此前已经被过滤掉的音节；正常但错误的译文也不一定触发复核 |
| 断线 | 重连期间没有可用连接的音频不补发，旧连接的声音不重放 | 连接恢复不等于中间内容补全；这是明确的完整性缺口 |
| 自动互译连接数 | LiveTranslate 系列自动中法互译使用两条连接；Audio/Omni 使用一条 | 同一声音发送次数不同，质量与成本对比必须记录该差异，不能仅比较模型单价；实际计费以用量与账单为准 |

## 完整流程与每一环可以调什么

“现有”表示已经能在应用内修改；“拟开放”表示需要实现与测试，目前不能在手机上调。

### 1. 从哪里拿声音

- **现有：麦克风来源**，系统自动、手机或耳机。仅影响实际收音的功能，不影响直接采集其他应用声音。
- **现有：字幕来源应用**，例如 WhatsApp Business。系统播放采集直接取允许共享的应用声音，不是让麦克风再听一遍扬声器。
- **拟开放：本功能的源语言提示**，默认自动中法互译；高级页可临时锁定法语或中文用于比较，模型不支持时不给无效开关。
- **不作为日常调节项：采样格式**，由设备与模型能力匹配。当前采集尝试 16k/48k，云端传输转为 16k 单声道；随意提高数字不等于提升原音质量。

系统不允许共享的声音，不能靠增加灵敏度或更换模型解决。

### 2. 判断人声，处理噪声和回声

这里是两个问题：背景噪声应少送入模型；应用自己的朗读不应被当成新说话。

| 拟开放选项 | 调高或延长 | 调低或缩短 |
|---|---|---|
| 人声过滤严格程度 | 更难把雨声、杂音当人声；更可能漏轻声 | 更容易保留轻声；更可能引入噪声 |
| 确认有人说话的等待 | 减少短噪声触发；需要更长句首回溯补偿 | 起声快；短噪声更容易通过 |
| 保留句首的时长 | 更好保住轻声开头；多带入一点前置噪声 | 缓存更少；更容易缺句首 |
| 保留句尾的时长 | 少吞尾音和短停顿；多带入尾部噪声 | 更干净利落；可能切掉尾音 |
| 播报中抢话灵敏度，仅麦克风监听 | 更容易打断；误打断风险更高 | 误打断少；轻声抢话可能不起效 |

当前过滤内部值：人声开始判断 0.52、持续判断 0.32；连续两个 32 毫秒窗口确认；普通句首回溯 192 毫秒；句尾保留约 256 毫秒；疑似抢话回溯最多 640 毫秒。这些是算法判断值，**不是 52% 的识别准确率**。

建议屏幕字幕和麦克风监听分别保存配置。先用固定声音比较轻过滤、当前过滤、旁路过滤的保真率与误识别，不能直接假设“所有过滤关掉”或“过滤越强越好”。复核用的临时原音应在破坏性过滤之前保留，默认只在内存、有时限，结束清除。

### 3. 什么时候让模型翻译一句

- **拟开放：停顿多久提交一句**。短一些出字快，但换气就容易分句；长一些句子完整，但等待增加。
- **拟开放：断句方式**。仅展示该模型真正支持且应用已适配的方式，例如按停顿、由应用提交、理解意思后断句。
- **拟开放：连续无停顿时的最长处理片段**。防止几分钟说不停就一直没有最终结果；它是内部处理边界，不应拆开用户的一条语音记录。具体范围须根据所选接口验证，不能伪装成所有模型通用参数。
- **固定的正确性要求：后一句不能悄悄丢掉前一句译文**。这不是交给用户选择是否开启的功能。

Audio 3.1 和 LiveTranslate 3.5 官方允许的停顿范围是 0.2～6 秒；Audio 3.1 的语义断句方式下，停顿秒数不生效。LiveTranslate 3.8 当前使用的说话人检测阈值官方固定为 0.5，不能造出一个看似可调的滑块。

不要直接把 Audio 的语义断句当成解决方案：它面向对话，可能忽略“嗯、啊”或无效轮次；应用还必须适配这些事件，并验证它适不适合逐字忠实翻译。

### 4. 听写与翻译：两种不同路线

**分步路线：声音 → 原文 → 译文 → 按需朗读。**

可以分别挑听写、文字翻译、朗读模型。原文已经错了，换更贵的文字翻译模型通常不能补回缺失的声音。优点是容易定位错误、纠错后可只重译；代价是多阶段等待和调用。目前默认按住说话使用这条路线，实时监听尚没有完整的分步流式路线。

**一体路线：声音 → 模型同时返回原文、译文和可选译音。**

LiveTranslate 为专用翻译；Audio/Omni 依靠翻译指令约束行为。一体模型内部听写并不由设置里的独立听写型号随意替换。更改独立听写或文字翻译模型，不会自动改变一体模型的日常输出，只影响真正走到它们的分步处理、重译或异常复核。

拟开放且必须按能力筛选的选项：

- 本功能使用的一体模型，或已实现的分步路线。
- 专有名词与固定译法，例如人名、公司名、产品名。接口支持词汇表才发送；不支持则说明限制。
- 翻译要求，例如忠实完整、保留数字与否定、不回答原话中的问题。允许编辑的补充要求仅作用于支持指令的模型。
- 参考前文的范围。多参考有助于代词和上下文，但可能带入旧话题并增加处理成本；同一媒体语音的内部句子与不同语音之间应区别处理。
- Audio 3.1 当前上下文为 1 轮，官方支持 1～50 轮；增加轮数不是免费提升质量，应在同样长语音上比较。

### 5. 哪些句子属于同一条语音

**拟新增独立的合并层，而不是靠停顿断句参数实现。**

- 播放中的同一条语音持续追加原文和译文，内部可分句处理，换气不清空。
- 若能可靠获得目标播放器的停止状态，在停止持续 2 秒后结束这一段；该等待时间可配置。
- 新语音有可靠标识时优先用标识区分，不依靠音量猜测。
- 若只拿到音频，没有可靠来源状态，就无法保证区分“语音中间的长静音”和“已经播完”。必须明确显示边界判定不可用，并提供“开始新段”，不能把静音计时冒充来源停止。
- Android 能报告播放活动，但不保证提供 WhatsApp 每一条语音的身份；获取其他应用媒体会话还有权限和对方是否提供会话的条件。具体能力须 Fold5 真机核验，不承诺仅凭电脑调试权限永久解决。

### 6. 出错、断线和异常复核

| 拟开放选项 | 收益 | 代价或边界 |
|---|---|---|
| 异常时自动复核 | 对机械重复、明显语种异常重听原音 | 额外等待与调用；不保证纠正一切错误 |
| 复核使用的听写、翻译模型 | 可以独立比较 | 不改变此前已经正确走完的一体模型句子 |
| 临时音频保留时长 | 能复核更早的完整片段 | 内存与隐私暴露时间增加；默认不永久保存 |
| 每段最多复核次数与费用约束 | 限制反复调用 | 达到上限后应明确提示未确认，不能悄悄丢句 |
| 重连次数、等待上限 | 适应短暂网络抖动 | 增加等待；不应显示没有截止时间的“连接中” |
| 断线片段补齐策略 | 有界缓存后补译可减少漏句 | 需保证顺序、去重与原始时间位置，并防止无界积压 |

当前异常复核：90 秒循环缓存、单片段最多 60 秒、最多两个待复核任务、停止时最多等 6 秒。当前重连间隔为 0.7、1.8、3.5 秒。数值不是用户界面已有选项。

连接状态建议明确区分“连接服务”“声音已送出”“正在识别”“正在翻译”“连接中断，等待补齐”“本段未完成”。不要把这些状态全写成“连接千问中”。

### 7. 屏幕字幕和历史怎么显示

- **现有：**长文本自动跟随、手动回看、回到最新、全文。
- **拟开放：**字号、浮窗高度、原文/译文显示方式、紧凑程度、临时文字与确认文字的展示方式。
- **拟新增：**按整条语音显示，内部句子可展开；不把每句都变成独立大卡片。
- 调整显示不应改变发送给模型的内容；显示容量也不应成为截断持久历史的理由。长列表用按需渲染处理性能，不用无上限的单个文本控件堆积。

### 8. 朗读和重播

- **现有：**自动朗读、耳机/机身分路、手动重播优先耳机、单独朗读模型。
- **拟开放：**支持的音色与语速、复用当次译音或重新生成的明确选项。
- 一体模型当场返回的译音，与后来用文字重新生成的声音不是同一次调用。设置应直接说明本次使用哪一种；缓存失效时也要说明，不应看起来切了型号却还在播旧声音。
- 屏幕字幕维持只出文字，除非用户主动重播，不为字幕额外生成译音。

### 9. 账号和费用

- 账号、地域、业务空间放在单独的连接页，不混进日常调参。业务空间不是免费模型专区，付费也不代表所有地域、接口和型号任意互换。
- 展示所选模型、服务确认的型号、调用次数、可获得的用量；服务没有报告的项目标为未知。
- 不把未知费用写成零，也不把测试预算预留写成实际消费。
- 调参比较一次只改一个变量；相同声音、相同翻译方向、相同输出方式，对比完整性、原文错误、译文质量、首字等待与实际用量。

## 设置重整建议：等待用户确认，尚未实施

以下是前一轮提出的候选结构；以文首“用户参与的边界”为准。先确定算法与体验，再决定哪些少量选项值得出现在日常设置，不能按内部参数清单机械扩建界面。

三条路线：仅加参数最快，但不能解决记录边界和漏句；只做自动优化最简单，但缺少用户要求的控制；建议采用“基础默认 + 分功能调校 + 对比记录”。

- 独立设置页，首层只放“统一方案”“按功能调整”“账号连接”。合屏逐页，展开时可用分类与详情双栏。
- 每个功能再按“声音 → 分句 → 翻译 → 显示 → 朗读”进入设置，不先展示七个技术模型清单。
- 高级项说明当前值、作用、调大/调小的代价、适用范围；不支持的项说明原因，没有无效开关。
- 显示哪些功能跟随统一方案、哪些已经单独修改；改变整套方案时明确处理单项设置，不悄悄清掉。
- 保存自定义方案、复制、恢复默认、回到上次配置；可导出不含密钥和私人原音的配置。
- 配置按版本持久化并一次保存；录音开始时固定本次配置，避免边听边切换导致前后不一致。
- 增加可自动调用的诊断接口：声音收到多少、过滤多少、发出多少、模型分句数、完成/取消数、重连与补齐数。它们用于定位，不冒充语义准确率。

先补自动化失败用例：连续长句、换气、15 秒静音但播放器仍在运行、播放器停止后 2 秒、译文未完成时下一句到达、返回事件乱序、雨声、轻声、断线期间音频补齐和配置恢复。再比较同一份固定录音，最后核验真实 WhatsApp 播放状态与实际体验。前两步不能替代最后一步。
