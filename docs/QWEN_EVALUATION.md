# Qwen 模型与成本调研

>
> 如果识别不了是不是同一段声音，那就只要声音源消失后（注意不是声音消失后，因为一段声音可能中间有很长时间的停顿没有声音）2秒钟，则识别为新的一段声音并开始翻译。

## 2. 当前调用链：代码能证明什么

| 功能 | 当前调用 | 可核对位置 |
|---|---|---|
| 按住说话 | Qwen3 ASR Flash 听写，再用 Qwen MT Flash 翻译；需要朗读时才合成 | `ConversationTranslator.kt`、`ConversationVoice.kt` |
| 打字 / 修改原文后重译 | 文字翻译，不重新听写 | `ConversationTranslator.kt` |
| 重播 | 优先用已有音频；缓存缺失时调用 Qwen3 TTS Flash | `ConversationVoice.kt`、`VoiceClips.kt` |
| 自由监听 | LiveTranslate 3.5，要求文字和音频输出 | `LiveDesk.kt`、`QwenLiveSession.kt` |
| 屏幕字幕 | LiveTranslate 3.5，只要求文字输出；长机械重复才另做一次听写和翻译复核 | `QwenSpeech.kt`、`RecoveringCaptionSession.kt` |

这不是每句话同时调用四种模型。历史自动化云端验收也会产生调用，现有计数无法把它与日常使用准确拆开。

明确的工程成本风险：

1. `QwenLiveSession` 同时开两个固定目标语言连接，同一音频发送两次，再按源语言选择结果。这是当前自动中法互译的实现方式，不是理想的成本设计。双路也须等待双方就绪；不能把这点直接认定为全部连接卡顿的原因。
2. `VoiceClips` 是按会话记录、文字、音色、模型索引的 8 MiB 内存缓存；进程重启、淘汰或同文不同记录可能再次合成。持久化、跨记录复用值得评估，但需要明确清理与隐私边界，尚未实现。
3. 屏幕字幕本来就没有申请译音，不应把“关闭屏幕字幕 TTS”当作新的节省成果。
4. 重连时当前代码不补发中断期间音频。替换模型不能修复未送达的内容；模型比较必须把原始采集、过滤后音频、实际送出、云端原文/译文、最终保存分别核对。

尚未确诊：0.5.6 跨应用测试中两次有声音而无最终字幕的原因，以及用户这次“连接千问中”的具体原因。详见 [验收进度](NEXT_TASKS.md)。

## 4. 比较方法：先过质量门槛，再比较价格

不把质量、速度和价格揉成一个可用低价抵消漏句的总分。先设最低可用标准，再在合格方案中比较成本与速度。没有实测前只给候选顺序，不给“最佳模型”结论。

### 4.1 相同输入、两层验证

1. **模型层**：相同的固定音频、相同速度、相同语种任务分别直送模型；不经过手机的人声过滤，原音与预期原文已知。记录音频时间覆盖、服务端事件计数、最终原文/译文、用量和错误。仅固定样本的文字可保存，不保存密钥或个人录音。
2. **产品层**：胜出候选和旧基线接入相同的手机采集、过滤、字幕、历史接口。对比过滤前后与发往云端的覆盖率，核对显示与持久化结果。这样可以区分模型错误、客户端解析错误和输入缺损。

厂商、区域、网络、音量、输入采样率和测试素材保持一致；测试顺序轮换。首轮不人为断网，先比较正常能力，随后单独做连接中断的故障测试。失败全记入结果，不“重跑到成功”或只公布成功轮次。

### 4.2 样本设计

- 短中文、短法语、正常长句和多句消息；保留现有固定录音基线，不能只依赖单一 TTS 音色。
- 至少一段多分钟语音，中间有 2、5、15 秒自然静音；末尾一句短且重要，用于检查尾句。
- 两条紧邻语音、不同说话人、同一个人连续两条、中法交替；分组边界另给受控播放事件，不要求模型猜 WhatsApp 消息编号。
- 数字、金额、日期、时间、姓名和否定句；原文含问句、命令、要求“别翻译”的句子。模型必须忠实翻译，不能回答问题或服从待翻译音频中的指令。
- 纯雨声、语音加雨声、低音量、聊天应用编码后的声音。自然法语口音素材必须有许可和可靠参考文本；若暂缺，报告覆盖缺口，不能以合成音通过代替。
- 仅在产品层添加网络中断、恢复、迟到结果、停止与下一条开始的交错。断线补齐既不能漏内容，也不能重复追加。

### 4.3 指标与拟议门槛

| 指标 | 记录方式 / 拟议判定 |
|---|---|
| 原文完整性 | 法语词错误率、中文字符错误率；逐句核对是否缺失，不用“出现关键词”代替全文完整 |
| 翻译忠实性 | 对预设信息点评分，数字/金额/时间/否定错误单列；参考译文允许合理同义，不逐字硬匹配 |
| 致命错误 | 漏整句、循环刷屏、用回答代替翻译、关键数字/否定反转、静音新增内容：该样本失败，不能靠低价抵消 |
| 实时性 | 分开记录首个原文字、首个可理解译句、后续稳定译文、播放结束到最终完成；中位数与较慢的 95% 分位均报告；拟议译文延迟目标 95% 分位不超过 4 秒，超标原因单列 |
| 连贯性 | 长停顿后旧内容仍在、继续增长；前文是否被撤掉、重复或错误替换；全程不等待整段结束才出译文 |
| 可靠性 | 每次建连/识别/翻译/保存是否成功，服务超时、限流、空结果分别计数；小样通过不视为长期保证 |
| 成本 | 音频/文字输入与输出分别计量，计入失败、重试、复核和历史上下文；屏幕字幕与含朗读的面对面分开算 |

语义评分采用预先整理的中法参考和信息点，不让同一个被测模型给自己打分。人工语言复核有争议时标为未确认。尽可能通过接口验证；不把多轮手机点按或听音工作转嫁给用户。

### 4.4 有限预算的筛选，而不是所有模型长期并跑

拟议分三步，预算尚待用户确认：

1. 离线解析/状态测试先通过，再给每个新候选最多一分钟固定声音做兼容、语言、文字输出、实际计量初筛。不可用或直接不满足中法翻译的候选停止，不无休止重试。
2. 只让两条有希望的路线和旧基线进入完整样本集；建议约 12 分钟素材，每条路线两轮。模型实际收到的时长按所有连接相加，旧基线两路输入不能按单路算。
3. 只给胜出方案做手机端集成验收；面对面朗读另开短测试，不在屏幕字幕比较中生成或播放译音。

建议首轮总费用预算 10 元，不以免费额度当成零成本。需先确认实际地域、访问权限和可用计量；每次请求前预留其有界最坏成本。输出长度、时长、重试次数必须有上限；用量缺失或无法给下一请求合理费用上界时停止，不继续盲试。平台账单可能延迟，接口估算和账单金额分开呈现，不能承诺靠事后轮询实现绝对即时扣费封顶。

## 5. 尚未选定的建议方向

- **屏幕字幕**：优先比较 Audio 3.1 Flash 和专用 ASR Streaming + MT 的成本/完整性，用 LiveTranslate 3.8 验证专用同传是否在实时性上值得额外费用。Omni 做同价短样本对照，不因功能多而直接作为默认。
- **面对面按住说话 / 自由监听**：不能直接照搬字幕胜出结果；有译音、抢话、原文显示等额外要求。可在字幕结论后评估 Audio 3.1 的音文一体输出与原有链路。
- **按需调用**：字幕只要文字，不调用 TTS；重播优先复用已经生成的声音；不同时跑所有候选；不在主模型正常时每句调用另一模型“保险”。
- **避免双路重复发送**：研究单次识别后决定方向，或一个支持严格双向翻译的连接。必须连同识别方向所需成本、等待时间和开头缓存一起评估，不能只删除一条连接导致另一个方向失效。
- **保持记录与模型解耦**：播放来源/消息分组、原文/译文追加、断线补齐由应用保证。无法取得来源状态时不把静音等同播放结束。模型更换不改变用户已确认的边播边译需求。
- **可维护配置**：候选模型、地域单价、超时和预算进入独立配置；每轮证据记录版本与参数。正式界面优先展示容易理解的方案名和用量，不要求用户理解所有模型字符串。

以上只是调研建议。下一步先确认测试范围与预算，再编写和验证隔离的评测接口；不得以本调研作为已完成模型替换、已修复漏译或已证明节省的依据。
